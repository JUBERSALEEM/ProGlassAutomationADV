# ProGlass Automation — website

The marketing and product website for the ProGlass Automation desktop
application. It is a Next.js (App Router) + TypeScript project that lives
entirely in this folder. It does not build, reference or modify the WPF
application, and nothing in this folder is part of the shipped product.

## Running it

```bash
npm install
npm run dev        # http://localhost:3000
```

```bash
npm run lint          # eslint src scripts
npm run typecheck     # tsc --noEmit
npm run test:job-orders # release gate and production routing semantics
npm run build         # production build, all pages prerendered
npm run start      # serve the production build
```

Optional, after a build is being served:

```bash
python3 scripts/audit-site.py            # crawl http://127.0.0.1:3000
python3 scripts/audit-site.py https://…  # or any deployed origin
```

If a build or a dev server is already failing, **`npm run fix`** is the one
command that repairs the state: it installs whatever is missing, clears the
build cache, reports which revision it just repaired, and tells you what to run
next. `npm run doctor` only reports.

Run `npm run doctor` at any time to see the revision in the tree, whether every
declared dependency is installed, and whether anything under `src/` imports a
package `package.json` does not declare.

The site's runtime dependencies are Next, React, React DOM and `fflate` (used
to generate XLSX files server-side). Markdown for the blog is parsed by
`src/lib/markdown.ts`, written for this project, so blog parsing depends on
nothing that can go missing from a package registry.

The audit checks every internal link and image, the per-page metadata
(title, description, canonical, Open Graph, viewport), one-`h1`-per-page,
missing image `alt` text, and a list of banned marketing phrases.

See **[docs/DEPLOYMENT.md](docs/DEPLOYMENT.md)** — a step-by-step guide from this


| `--brand-100/200/300/400` | the rest of the ramp | `Sp.PaneLight`, `Sp.Pane`, `Sp.FaceTop/Left/Right` — the floating panes and the isometric emblem |
| `--ink-950` (daylight) | `#F8F5EE` | `Sp.Canvas` — the warm ivory studio ground, not a cold white |
| `--line` (daylight) | `#D6CDE9` | `Sp.Keyline` — the divider rule under the wordmark |
| `--text-1` (daylight) | `#241B3A` | `Sp.Ink` |

`src/components/brand/GlassCubeEmblem.tsx` carries the application's emblem — the
three face paths are transcribed coordinate-for-coordinate from the splash's
`Viewbox`/`Grid Width="160" Height="170"`, so the mark on the site is the same
drawing as the mark the product opens with, at any size.

Five cosmetic layers sit on top of the tokens, all in the `@layer components`
block at the foot of `src/app/globals.css`:

| Class | What it is |
|---|---|
| `.aurora-field` | three saturated washes crossing a band, drifting on a 34 s cycle — one paint, from `--aurora-image` |
| `.orb` / `.orb-wide` | a pool of light drawn as a radial gradient; the caller sets `--orb` to its colour and gives the element its size |
| `.edge-conic` | a hairline of accent light around a card, revealed on hover by an opacity transition |
| `.spot` | a light that follows the pointer across a card's face — driven by `src/lib/useSpotlight.ts` |
| `.bento`, `.spine`, `.marquee`, `.panel-feature`, `.figure` | the layout patterns the redesigned pages are built from |

Every one of them reads `--brand-*`, `--glass-*` or `--wall-*`, so switching
mode or palette family repaints all of them with no markup change, and every one
degrades to nothing: with `prefers-reduced-motion`, with scripting off, or on a
touch device the content is still complete and still readable.

The page's own surface — the wallpaper's nine gradient layers and the noise tile
that finishes them — is the `body::after` background stack rather than a class.
It is one paint, and nothing in it is composited against the content above it.

### The performance contract

Three things nearly cost this site its responsiveness, and all three were
decoration. They are banned, and the bans are the point of this section:

| Never | Why | Instead |
|---|---|---|
| `mix-blend-mode` on a full-viewport layer | the browser re-blends the whole document on every scroll frame, and the page drops off Chromium's GPU fast paths | an alpha token — `--aurora-1/2/3` — or a heavier colour in the gradient itself |
| `@property` plus a keyframed gradient angle | a conic-gradient repaint per frame, per element, on every unhovered card on the page | a static ring, revealed by an `opacity` transition |
| `filter: blur()` more than a few pixels wide | a multi-pass kernel over a 20 rem element, re-run whenever it changes | `.orb` — the same light as a radial gradient, one paint |

The rule underneath all three: **a decorative layer may animate `transform` or
`opacity`, or nothing at all.** The aurora drifts with `translate3d`, the edge
ring fades in, the spot follows the pointer. None of them repaints, and the
texture survives every one of them — the aurora still crosses the opening
screen, the grain still finishes the surface, the cards still catch the light.

Check it after a design change, from `website/`:

```bash
npx tsc --noEmit && npm run lint && npm run build
python3 scripts/audit-site.py http://127.0.0.1:3000
python3 scripts/audit-site.py --fresh                        # also: is the server the build it claims?
grep -rn "mix-blend-mode\|blur-\[" src/ --include=*.tsx    # expect no hits
```

### Which build is this?

The top panel prints a build stamp — the date, the time in UTC and the branch —
and `/api/health` serves the same facts as JSON:

```bash
curl -s http://127.0.0.1:3000/api/health
curl -s https://proglassautomationadv-website-tkim.vercel.app/api/health
```

The site is deployed from one repository to more than one host, and each host
builds the branch at its own moment, so two deploys of the same commit can be
hours apart while looking identical. The stamp is how that stops being
invisible. `scripts/audit-site.py --fresh` reads the endpoint, reads the stamp
the page itself prints, and fails if the origin is serving a different revision
from the one the tree is on — point it at a preview URL or the live site and the
answer is the desync, named.

`npm run check:live` asks the same question of every origin the site is meant to
be reachable at, in one line each, and exits non-zero if any of them is behind:

```bash
npm run check:live
npm run check:live https://a-preview-url.vercel.app
```

```
live            https://proglassautomationadv-website-tkim.vercel.app
                422172c · 2026-10-07T11:50:56.640Z · production
                CURRENT — it is running the revision the branch is on
```

The three answers it can give are worth knowing apart: **current**, **behind**
(the deployment exists; production has not been pointed at it — the fix is the
project's Production Branch setting), and **no stamp** (the origin answers with
the site's own 404 for `/api/health`, so the build predates the stamp at all).
The third is the dangerous one, because the site looks perfectly healthy while
being months behind. The values are inlined at build time by the `env`
block in `next.config.ts` (see `scripts/build-stamp.mjs`), so a page prerendered
during the build and a route handler starting cold later report the same instant.

### The top panel's budget

The header is the one part of the site whose width can be worked out exactly:
a fixed-height row of fixed-size things, and the only unknown in the arithmetic
is how wide a word is — which is not unknown, because the font files are in
`src/fonts` and `scripts/measure-panel.py` reads the advance widths straight out
of them at the right weight.

That matters because the panel must not squeeze. Everything in it is a flex item
in a `nowrap` row, so a row that is over budget does not overflow politely: the
flexible children shrink and their labels wrap mid-phrase inside a bar whose
height is fixed — "Request a / Demo" — which reads as a broken header. Run the
script after touching the panel:

```bash
python3 scripts/measure-panel.py          # the ladder, with verdicts
python3 scripts/measure-panel.py --json   # the same numbers, machine-readable
```

Measured, the full row needs ~1616px of content width, and the panel sheds its
least important items in a fixed order on the way down so nothing is ever
squeezed. Every constant in the script carries the Tailwind class it was read
from:

| Tier | From | What the panel shows | Needs / has |
|---|---|---|---|
| `wide` | 1920 | everything: nav with glyph icons, palette word, both CTAs, stamp | 1616 / 1777 |
| `2xl` | 1536 | nav, palette word, primary CTA, stamp — no ghost shortcut | 1338 / 1393 |
| `xl` | 1280 | nav without glyph icons, settings, stamp — no CTA, no palette word | 1105 / 1169 |
| `lg` | 1024 | Menu button, settings, primary CTA, stamp — no nav pill | 882 / 929 |
| `sm` | 640 | wordmark, language, reading switch, palette, menu button | 431 / 569 |
| phone | 360 | mark alone, palette, menu button — no wordmark, no language button | 182 / 305 |

Two of those entries are worth their own sentence, because both are visible
choices rather than accidents:

- between 1024 and 1279 the primary nav opens from a **Menu button** in the
  settings cluster instead of sitting in the row — the same sheet the phone menu
  uses, and the same markup;
- on phones the lockup drops to the **mark alone** and the language button
  waits for `sm`. The row is then 182px in the 305px a 360px screen leaves it,
  which is the difference between a header that fits every phone and one that
  fits the ones we happened to measure. The full lockup is in the footer on
  every screen, and all fifteen languages are spelled out in the sheet, one tap
  away.

The one that surprises people is `lg`: 1024 is not wide enough for the six nav
cards *and* the settings *and* the stamp, so between 1024 and 1279 the primary
nav opens from a Menu button in the settings cluster — the same sheet the phone
menu uses — and the nav pill returns at `xl`. The order is deliberate: identity,
menu access, settings and the build stamp are kept longest; the ghost shortcut
to the screenshots is shed first, because its destination is the first child of
the Product menu.

### The plates

The hero backdrop and the brand banner are drawn from the site's own tokens by
`scripts/render-hero-backdrop.mts` and `scripts/render-hero-banner.mts`, through
`sharp` — no headless browser is involved, so the artwork is reproducible from
the repository alone. Both read `[data-theme="midnight"]` straight out of
`src/app/globals.css` through `scripts/lib/theme-tokens.mts`: the private colour
copies they used to carry went stale the moment the palette was deepened, and a
plate that is drawn in last month's violet is worse than no plate at all. A
token that is renamed now stops the render rather than silently falling back.

```bash
npm run assets:plates     # re-render both masters, then re-encode the derivatives
```

Masters land in `public/images/brand/` at 3840 px wide (plus `README_ASSETS/hero.png`
for the repository's front page), and `npm run assets:optimize` writes the
AVIF / WebP / PNG derivatives at 1280–3840 into `public/images/brand` and
`public/images/glass3d`. Pages reach them through `src/data/assets.ts` — the
metadata icons included, which is why nothing in `src/` hard-codes a path into
`public/`.

### Typography

Inter, IBM Plex Sans, Source Serif 4 and JetBrains Mono are self-hosted from
`src/fonts`, and the appearance studio can set the whole site in any of twelve
more families the visitor's own machine already has. The display scale
(`.display-hero`, `.display-1/2/3`) uses fluid `clamp()` sizes with tracking that
tightens as the size grows, and `.figure` / `.figure-lg` / `.figure-md` set every
number in tabular mono so a column of them lines up.

## Operations data (Supabase)

The three operations views read the same Supabase project; every other page is
static and needs no environment at all. They are connected by design — shared
workbook scoping (`src/lib/source-scope.ts`), the same operator session
(`src/lib/useOperatorSession.ts`), and a document chain in this order:
Proforma Invoice → Job Order → Delivery Note → Tax Invoice → Statement. The
first three have live website views; Tax Invoice and Statement link to their
product overviews until their live operations views are built.

All three operations pages export the full filtered result set (not only the
visible page) to CSV and Excel. Delivery Excel includes a PI summary and a
separate movement ledger. Exports are capped at 10,000 rows and refuse
truncated data. PDF is rendered server-side with `@react-pdf/renderer`; see
**[docs/OPERATIONS_EXPORTS_ANALYSIS.md](docs/OPERATIONS_EXPORTS_ANALYSIS.md)** for
the layout, safety limits and follow-up recommendations.

| Variable | Used by | Notes |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | all three dashboards | Project address |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | all three dashboards | Publishable key; Row Level Security decides what it may read. The service key is refused if pasted here |
| `PROGLASS_CONFIRMED_STATUSES` | `/deliveries` | Server-side. Which `public.records.status` values count as a delivery obligation. Defaults to `Confirmed`; widen with `"Confirmed,In Production,Ready"`. `/job-orders` intentionally stays strict and accepts only `Confirmed`. |

Three SQL files are applied manually in the Supabase SQL editor, in this order:

```
supabase-dashboard.sql    public.records: active/workbook columns, aggregation
                          RPCs and indexes (required first)
supabase-job-orders.sql   website production release snapshots, stage quantities,
                          progress audit and authenticated RPCs
supabase-deliveries.sql   public.delivery_entries: delivery ledger, balance view,
                          indexes and optional over-delivery guard
```

The Job Orders migration creates a separate Supabase production tracker. It does
not change Excel Sync's `public.records` rows or the Windows desktop database.
If the delivery migration is not installed, the delivery tracker still shows
confirmed PIs as awaiting dispatch and explains the missing ledger. The delivery
rules and rollout are in **[docs/DELIVERY_TRACKING_ANALYSIS.md](docs/DELIVERY_TRACKING_ANALYSIS.md)**; production release design and known source-data limits are in **[docs/JOB_ORDER_PRODUCTION_TRACKING.md](docs/JOB_ORDER_PRODUCTION_TRACKING.md)**.

Every drawing of a plate on this site is generated, not stored, and they all come

```

  sheetPlan.ts                  the homepage's sample job and its margins

  PlateSchedule.tsx             the piece cutting schedule for one sheet
  CadLegend.tsx                 the key, transcribed from the application's
  PlateInspector.tsx            canvas + schedule + gallery, wired together
```

The plate geometry — the usable rectangle, the breakout band and the 200 mm

converted to millimetres, so a responsive drawing drops a label that would not
fit rather than smudging one on.

## Languages

The site ships the application's own fifteen languages: English (the bare
addresses), Arabic, Bengali, German, Spanish, French, Hindi, Indonesian,
Japanese, Korean, Portuguese, Russian, Turkish, Urdu and Chinese. Two of them —
Arabic and Urdu — are right-to-left, and the whole tree lays out for that.

**A visitor is not asked which language they want.** The first request is
resolved in `src/proxy.ts`, in this order: the cookie the language menu wrote
last time, the country header (`x-vercel-ip-country`), the browser's own
`Accept-Language`, then English. A visitor from Germany lands on `/de-DE/…`
without a splash page; the language menu in the header of every page switches
it, keeps the page you were reading, and remembers the answer.

**Nothing is translated by hand twice.** A sentence is looked up in the site's
dictionary, then in the application's own language file — indexed by its English
value — and then shown in English. That second step is the important one: a
proforma, a job order, a delivery note, a production stage and a base rate are
called what `Themes/Languages/<code>.xaml` calls them, so the website and the
software cannot drift apart.

The menu also states how complete each language is — computed from the
dictionary in the build — and tells the reader that the browser's own
translation can carry the remainder. That is a deliberate division of labour
rather than a fallback: the shipped dictionaries carry the product's words and
the real figures, the browser carries the prose nobody has filled yet, and
everything that is data rather than prose (spec names, serials, module keys,
the brand) is marked `translate="no"` so no translator rewrites it.

The whole pipeline — how keys are extracted, how a language is filled, how
coverage is measured, and how to see what English is still on a page — is in
[`src/i18n/README.md`](src/i18n/README.md). That file also carries the measured
breakdown of *why* a page can still read English after the language is changed:
an untranslated sentence, a sentence no `t()` reaches, or two known strings the
markup glued together — three different defects with three different fixes.

Translating a whole language is one command on a machine with internet:

```bash
cd website
node scripts/i18n-memory-fill.mjs --locale fr-FR    # the application's own wording, where it exists
node scripts/i18n-machine-fill.mjs --locale fr-FR   # the rest, masked, validated, applied
node --experimental-strip-types scripts/i18n-audit.mjs
```

and a two-half hand-relay exists for a machine without it (`--split` / `--print`
/ `--ingest`). All three paths write through `i18n-apply.mjs`, so there is one
writer into `src/i18n/dict/<locale>.ts` and one place where a bad row is
refused.

## The honesty rules this site is built on

These are not style preferences; breaking one is a defect:

1. **Every product statement is traceable to the WPF source tree.** Most
   content records an `evidence` path naming the file that defines the
   behaviour, and several pages render it.
2. **No invented numbers.** There is no savings percentage, customer count,
   award, certification or performance claim anywhere. The counts that do
   appear (view areas, databases, test methods, languages) are measured from
   the application tree, labelled with the date and the method.
3. **No fabricated screenshots.** `src/data/screenshots.ts` gives every entry a
   `source` of `capture`, `repo` or `pending`. `pending` renders an explicit
   "capture pending" plate carrying the real window chrome — never a mock-up
   presented as the application.
4. **No SaaS vocabulary and no cloud claims.** No account, no tenancy, no
   subscription dashboard. The allowed calls to action are Request a Demo,
   Contact, Get in Touch and Learn More.
5. **Licensing is described at customer level only.** `/legal/license` follows
   `docs/LICENSE.md`: the licence file, activation paths, trial, grace and
   device activations. It deliberately does not describe how a licence is
   produced or validated.

When adding a page, follow the same pattern: put the facts in `src/data/`,
name the evidence, and state the limit of what is being claimed.

## Adding a screenshot

1. Capture the real screen and save it to
   `public/images/<category>/<descriptive-kebab-case-name>.png` — for example
   `public/images/optimization/optimization-2d-view-single-sheet.png`.
2. In `src/data/screenshots.ts`, set `src` to that path, `width` and `height`
   to the real pixel size, and `source: "capture"`.
3. Run `npm run assets:optimize` if you want AVIF/WebP derivatives plus PNGs in
   the public folder. Add the source PNG back to `public/images/<category>/`
   first — the script is a no-op when its inputs are absent.
4. Re-run `scripts/audit-site.py` after a build to confirm the new file is
   served.

Until a real capture exists, leave the entry as `pending`. The placeholder
exists so that no page has to show something the product did not render.

A pending Optimization entry may also set `previewVariant` to `settings`, `2d`
or `report`, which picks which screen of the module the interactive preview
draws. It exists because the site lists three of the module's tabs and one
preview was, for a while, shown under all three captions.

## Wiring the demo-request form

`src/app/api/demo-request/route.ts` is the single integration point. It
validates on the server and, with no transport configured, answers
`configured: false` and tells the visitor the message was not delivered —
the form never fakes a success.

To make it deliver:

1. Add your transport to the route (Resend, Postmark, SES, SendGrid, a webhook,
   or your own SMTP relay).
2. Put the credential in an environment variable. Nothing is read from the
   repository, and no credential belongs in it.
3. Set `DEMO_REQUEST_PROVIDER` so the route can report the truth about itself,
   and optionally `DEMO_REQUEST_INBOX` for the destination address.

The route stores nothing: no database, no server-side log of personal data.

## Notes

- Fonts are self-hosted from `src/fonts` through `next/font/local`, so no page
  makes a request to a third-party font host.
- Two kinds of image ship, and both are files this repository can produce from
  scratch: the real artwork from the WPF repository (`Resources/Glass3D/*` and
  the application icon), re-encoded at the widths the layout requests, and the
  two plates drawn from the site's own tokens by the renderers above. No stock
  photograph and no invented screenshot is served anywhere.
- Every decorative layer animates `transform` or `opacity` only, and the surface
  layers are single paintings rather than blends — see *The performance
  contract*.
- `prefers-reduced-motion: reduce` is honoured globally, and every animation
  collapses while its content stays visible.
