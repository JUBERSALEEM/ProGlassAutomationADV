# ProGlass Automation — website

The marketing and product website for the ProGlass Automation desktop
application. It is a Next.js (App Router) + TypeScript project that lives
entirely in this folder. It does not build, reference or modify the WPF
application, and nothing in this folder is part of the shipped product.

## Running it

```bash
npm install
npm run dev        # http://localhost:3000
```

```bash
npm run lint       # eslint src scripts
npm run typecheck  # tsc --noEmit
npm run build      # production build, all pages prerendered
npm run start      # serve the production build
```

Optional, after a build is being served:

```bash
python3 scripts/audit-site.py            # crawl http://127.0.0.1:3000
python3 scripts/audit-site.py https://…  # or any deployed origin
```

If a build or a dev server is already failing, **`npm run fix`** is the one
command that repairs the state: it installs whatever is missing, clears the
build cache, reports which revision it just repaired, and tells you what to run
next. `npm run doctor` only reports.

Run `npm run doctor` at any time to see the revision in the tree, whether every
declared dependency is installed, and whether anything under `src/` imports a
package `package.json` does not declare.

The site's runtime dependencies are Next, React, React DOM and `fflate` (used
to generate XLSX files server-side). Markdown for the blog is parsed by
`src/lib/markdown.ts`, written for this project, so blog parsing depends on
nothing that can go missing from a package registry.

The audit checks every internal link and image, the per-page metadata
(title, description, canonical, Open Graph, viewport), one-`h1`-per-page,
missing image `alt` text, and a list of banned marketing phrases.

## Deploying it

See **[docs/DEPLOYMENT.md](docs/DEPLOYMENT.md)** — a step-by-step guide from this
branch to `https://proglassautomation.com`, covering the Vercel project settings
(the site lives in `website/`, which is the one setting people get wrong), the
DNS records for the domain, the certificate, the launch checklist, and the
`Module not found` build error that appears when dependencies have not been
installed.

The short version, once the repository is on `main`:

```
Vercel → Add New → Project → import this repository
Root Directory: website      Node.js: 22.x
Configure Supabase for live operations data; PDF, CSV and Excel exports are generated by the Node server.
Deploy → then Settings → Domains → add the domain and its www form
→ add the two DNS records Vercel shows at your registrar → done
```

## Operations data (Supabase)

The three operations views read the same Supabase project; every other page is
static and needs no environment at all. They are connected by design — shared
workbook scoping (`src/lib/source-scope.ts`), the same operator session
(`src/lib/useOperatorSession.ts`), and a document chain in this order:
Proforma Invoice → Job Order → Delivery Note → Tax Invoice → Statement. The
first three have live website views; Tax Invoice and Statement link to their
product overviews until their live operations views are built.

All three operations pages export the full filtered result set (not only the
visible page) to CSV and Excel. Delivery Excel includes a PI summary and a
separate movement ledger. Exports are capped at 10,000 rows and refuse
truncated data. PDF is rendered server-side with `@react-pdf/renderer`; see
**[docs/OPERATIONS_EXPORTS_ANALYSIS.md](docs/OPERATIONS_EXPORTS_ANALYSIS.md)** for
the layout, safety limits and follow-up recommendations.

| Variable | Used by | Notes |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | all three dashboards | Project address |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | all three dashboards | Publishable key; Row Level Security decides what it may read. The service key is refused if pasted here |
| `PROGLASS_CONFIRMED_STATUSES` | `/deliveries` | Server-side. Which `public.records.status` values count as a delivery obligation. Defaults to `Confirmed`; widen with `"Confirmed,In Production,Ready"`. `/job-orders` intentionally stays strict and accepts only `Confirmed`. |

Two SQL files are meant to be run once, in the Supabase SQL editor:

```
supabase-dashboard.sql    public.records: soft-delete flag, source-file scoping,
                          aggregation RPC, indexes
supabase-deliveries.sql   public.delivery_entries: the delivery ledger, the
                          pi_delivery_balance view that owns the balance maths,
                          indexes, an opt-in over-delivery guard
```

Without the second file the deliveries tracker still runs: every confirmed PI
appears as awaiting dispatch and the page says why. The design reasoning — the
movement rules, the eligibility rule, the edge cases and the rollout — is in
**[docs/DELIVERY_TRACKING_ANALYSIS.md](docs/DELIVERY_TRACKING_ANALYSIS.md)**.

## Languages

The site ships the application's own fifteen languages: English (the bare
addresses), Arabic, Bengali, German, Spanish, French, Hindi, Indonesian,
Japanese, Korean, Portuguese, Russian, Turkish, Urdu and Chinese. Two of them —
Arabic and Urdu — are right-to-left, and the whole tree lays out for that.

**A visitor is not asked which language they want.** The first request is
resolved in `src/proxy.ts`, in this order: the cookie the language menu wrote
last time, the country header (`x-vercel-ip-country`), the browser's own
`Accept-Language`, then English. A visitor from Germany lands on `/de-DE/…`
without a splash page; the language menu in the header of every page switches
it, keeps the page you were reading, and remembers the answer.

**Nothing is translated by hand twice.** A sentence is looked up in the site's
dictionary, then in the application's own language file — indexed by its English
value — and then shown in English. That second step is the important one: a
proforma, a job order, a delivery note, a production stage and a base rate are
called what `Themes/Languages/<code>.xaml` calls them, so the website and the
software cannot drift apart.

The menu also states how complete each language is — computed from the
dictionary in the build — and tells the reader that the browser's own
translation can carry the remainder. That is a deliberate division of labour
rather than a fallback: the shipped dictionaries carry the product's words and
the real figures, the browser carries the prose nobody has filled yet, and
everything that is data rather than prose (spec names, serials, module keys,
the brand) is marked `translate="no"` so no translator rewrites it.

The whole pipeline — how keys are extracted, how a language is filled, how
coverage is measured, and how to see what English is still on a page — is in
[`src/i18n/README.md`](src/i18n/README.md). That file also carries the measured
breakdown of *why* a page can still read English after the language is changed:
an untranslated sentence, a sentence no `t()` reaches, or two known strings the
markup glued together — three different defects with three different fixes.

Translating a whole language is one command on a machine with internet:

```bash
cd website
node scripts/i18n-memory-fill.mjs --locale fr-FR    # the application's own wording, where it exists
node scripts/i18n-machine-fill.mjs --locale fr-FR   # the rest, masked, validated, applied
node --experimental-strip-types scripts/i18n-audit.mjs
```

and a two-half hand-relay exists for a machine without it (`--split` / `--print`
/ `--ingest`). All three paths write through `i18n-apply.mjs`, so there is one
writer into `src/i18n/dict/<locale>.ts` and one place where a bad row is
refused.

## The honesty rules this site is built on

These are not style preferences; breaking one is a defect:

1. **Every product statement is traceable to the WPF source tree.** Most
   content records an `evidence` path naming the file that defines the
   behaviour, and several pages render it.
2. **No invented numbers.** There is no savings percentage, customer count,
   award, certification or performance claim anywhere. The counts that do
   appear (view areas, databases, test methods, languages) are measured from
   the application tree, labelled with the date and the method.
3. **No fabricated screenshots.** `src/data/screenshots.ts` gives every entry a
   `source` of `capture`, `repo` or `pending`. `pending` renders an explicit
   "capture pending" plate carrying the real window chrome — never a mock-up
   presented as the application.
4. **No SaaS vocabulary and no cloud claims.** No account, no tenancy, no
   subscription dashboard. The allowed calls to action are Request a Demo,
   Contact, Get in Touch and Learn More.
5. **Licensing is described at customer level only.** `/legal/license` follows
   `docs/LICENSE.md`: the licence file, activation paths, trial, grace and
   device activations. It deliberately does not describe how a licence is
   produced or validated.

When adding a page, follow the same pattern: put the facts in `src/data/`,
name the evidence, and state the limit of what is being claimed.

## Adding a screenshot

1. Capture the real screen and save it to
   `public/images/<category>/<descriptive-kebab-case-name>.png` — for example
   `public/images/optimization/optimization-2d-view-single-sheet.png`.
2. In `src/data/screenshots.ts`, set `src` to that path, `width` and `height`
   to the real pixel size, and `source: "capture"`.
3. Run `npm run assets:optimize` if you want AVIF/WebP derivatives plus PNGs in
   the public folder. Add the source PNG back to `public/images/<category>/`
   first — the script is a no-op when its inputs are absent.
4. Re-run `scripts/audit-site.py` after a build to confirm the new file is
   served.

Until a real capture exists, leave the entry as `pending`. The placeholder
exists so that no page has to show something the product did not render.

## Wiring the demo-request form

`src/app/api/demo-request/route.ts` is the single integration point. It
validates on the server and, with no transport configured, answers
`configured: false` and tells the visitor the message was not delivered —
the form never fakes a success.

To make it deliver:

1. Add your transport to the route (Resend, Postmark, SES, SendGrid, a webhook,
   or your own SMTP relay).
2. Put the credential in an environment variable. Nothing is read from the
   repository, and no credential belongs in it.
3. Set `DEMO_REQUEST_PROVIDER` so the route can report the truth about itself,
   and optionally `DEMO_REQUEST_INBOX` for the destination address.

The route stores nothing: no database, no server-side log of personal data.

## Notes

- Fonts are self-hosted from `src/fonts` through `next/font/local`, so no page
  makes a request to a third-party font host.
- The only product imagery that ships is the real artwork from the WPF
  repository (`Resources/Glass3D/*`, the application icon and the brand
  banner), re-encoded to WebP at the widths the layout requests.
- `prefers-reduced-motion: reduce` is honoured globally, and every animation
  collapses while its content stays visible.
