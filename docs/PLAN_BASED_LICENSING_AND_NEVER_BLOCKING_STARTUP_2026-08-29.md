# Plan-Based Licensing & Never-Blocking Startup (2026-08-29)

> Senior analysis & implementation record for two user directives:
> 1. **"Main screen showing LICENSE PROBLEM when it should open normally…
>    should not block completely."**
> 2. **"Single button type GENERATE KEY based on 7 days / 30 days /
>    6 months / 1 year / 2 years… plans visible in the main app…
>    main app only accepts the key generated by the generator app.
>    No key-file nonsense. Simple activation method."**

## 1. Why the app showed "LICENSE PROBLEM" and hard-blocked

Startup chain at the previous commit:

```
LoadSecureOfflineLicense
 ├─ corrupt key/activation store          → Invalid  ← blocks
 ├─ legacy artifact present               → Invalid  ← blocks
 ├─ machine-fingerprint failure           → Invalid  ← blocks
 ├─ PreferTrialFallback
 │    ├─ ledger clock-rollback hard-fail  → Invalid  ← blocks
 │    └─ trial window exhausted + bad
 │        signed state                    → Invalid  ← blocks
```

`Invalid.CanRun == false` → `LicenseStatusViewModel.IsLicenseRequired`
→ full-screen `LicenseOverlay` (`IsClosable=False`) with the
"License problem" headline. So a user whose trial window had been issued
by an earlier build — and whose protected store no longer read cleanly
or held a legacy artifact — was locked out of the app entirely.

## 2. The fix — the app NEVER hard-blocks

`LicenseService` now normalizes every startup result through
`ResolveStartupFallback`:

```
runnable signed state (Valid / ExpiringSoon / Trial / Grace / TrialExpired)
    → as-is
else
    → AutoTrialManager.Resolve
        ├─ Trial (window open)            → working trial, full features
        ├─ TrialExpired (window over)     → read-only open (data preserved)
        └─ Invalid (clock rollback, etc.) → read-only open (data preserved)
```

- All four `Invalid` short-circuits in `LoadSecureOfflineLicense` now
  route through the fallback.
- `IsLicenseRequired` is now always `false` (the overlay stays in the
  XAML only as a dormant safety net, documented as such).
- Security consequence (intended): tamper evidence — corrupt store,
  ledger rollback — can never **grant** anything; it only degrades the
  app to read-only. The trial remains governed by the tamper-evident
  ledger, so corrupting the license store cannot buy trial time, and a
  rollback can never mint a fresh trial.
- A pasted license key restores full access at any time
  (`InstallKeyText` verifies before storing).

## 3. The generator — single-click, plan-based, no key files

The `.pgkey` load/create card is **deleted** (with the
`IssuerKeyMaterial` / `AppCompatibleIssuerKeys` classes). The vendor
tool is now literally:

```
[ 7 DAYS ]   [ 30 DAYS ]   [ 6 MONTHS ]   [ 1 YEAR ]*   [ 2 YEARS ]
        [ GENERATE LICENSE KEY ]   [ COPY KEY ]   [ SAVE KEY FILE… ]
```

- `LicenseGeneratorCore.Plans` = 7 / 30 / 182 / 365 / 730 days.
- Every key = Subscription license, full feature scope `"*"`, unbound
  (portable), signed by the embedded production pair, armored as
  `PGKEY1.<base64url(signed JSON)>`.
- The signing pair lives in
  `Tools/LicenseGenerator/ProductionSigningKey.cs` — **private half in
  the generator only**; the public half is mirrored in
  `Services/Licensing/LicensePublicKey.GeneratorCompatiblePublicKeyXml`
  and mapped by `TrustedLicenseKeys.All[keyId]`.
- Every generated key is self-verified against exactly that trust map
  before it is shown, so generate → paste → instant active is
  guaranteed by construction.

### Security trade-off (honest note)

The private key is now **embedded in the generator binary** instead of
an external file. Consequences:

- Anyone who obtains the generator (binary or source) can produce
  app-accepted keys. The generator must therefore be treated as a
  vendor-office tool: never shipped to customers, and this repository
  kept private. This is the accepted trade-off for the user's
  "no key-file nonsense" requirement.
- What the signature still buys you (unchanged): the customer app
  rejects **modified, refactored or cracked** keys — any byte change
  fails RSA-2048-PSS verification before anything is stored, and the
  pasted text must be a `PGKEY1`-armored block (raw JSON is refused).
  A test (`LicenseKeyEmbeddingTests`) pins that the app's trust ring
  accepts **exactly** the generator's public half and nothing else.
- Rotating the key later = one fresh pair, two constants
  (`ProductionSigningKey` + `LicensePublicKey`), rebuild both projects
  in the same release.

## 4. The app license page — plans visible + GET LICENSE KEY

`LicenseActivationView` now shows a PLANS card: the five plans as radio
choices with a **GET LICENSE KEY** button. It copies a ready-to-send
message (chosen plan + this PC's ID, marked "only if you bind the key")
and shows a preview dialog explaining the vendor replies with a PGKEY1
block. The paste-to-activate card stays the single activation action.

## 5. Tests updated

- `LicenseServiceTests`: legacy-artifact and corrupt-store scenarios now
  assert the **trial fallback** (and `CanRun == true`) instead of
  `Invalid`; a new corrupt key-store fallback test added.
- `LicenseKeyEmbeddingTests`: new test pinning app-trust-ring ⇔
  generator-public-half byte equality.
- `LicenseGeneratorSourceTests` / `LicenseGeneratorDesignSourceTests`:
  rewritten for the single-click plan design (plan radios, one generate
  button, no `.pgkey`/request/response strings).
- `OfflineLicensingHardeningSourceTests`: customer app still embeds no
  private material; activation view uses key/plan language only.

- Generator window resource keys all resolve against the generator
